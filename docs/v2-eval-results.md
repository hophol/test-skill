# V2 评测方法论的实测结果：两个旧方法抓不到的真发现

> 用 v2 方法论（区分度用例 + 过程验证 + 降级测试）对 us-breakdown skill 跑了一轮完整评测。
> 两个发现都是旧方法（只看结果）完全看不到的。

---

## 发现一：区分度用例暴露了 parser 脚本的一个真 bug

### 用例设计

构造了一个比旧用例更复杂的 US（多租户 SaaS 计费），其中：
- 3 条 AC 有显式编号（AC1:、AC2:、AC5:）
- 1 条 AC 以"当"开头（无编号）：parser 的关键词过滤器能匹配"当"
- 1 条 AC 以"此外"开头（无编号）：**parser 的关键词过滤器不匹配"此外"**

### 结果

- **with_skill 断言 must_contain_file 检查 AC4 → FAIL**（"missing AC4"）
- agent 正确跑了 parser 脚本，但 parser 本身漏掉了以"此外"开头的那条 AC
- 旧用例（us-login.md）的所有 AC 都有显式编号，这个 bug 从未暴露

### 为什么旧方法看不到

旧方法只测了"有编号的简单 US"——所有 AC 都以"AC1:"开头，parser 全部正确提取。
换一个格式不那么规范的 US，parser 的关键词过滤器就漏了。
**这就是文章说的"测试用例必须命中 Skill 真正介入的那个决策点"。**

### 意义

这说明 skill 的 parser 脚本在处理非标准格式的 AC 时有 bug——
"此外，租户管理员可以申请临时配额提升..."这条被漏掉了，
导致拆解结果只有 4 条 AC 而不是 5 条。
如果上线，这条验收标准对应的任务会被遗漏。

## 发现二：降级测试抓到了"工具挂了不停下来"的不可靠行为

### 用例设计

把 parser 脚本替换成一个会报错退出的 stub（模拟"工具不可用"场景），
然后验证 agent 的行为：
- **可靠行为**：尝试跑 parser → 失败 → 停下来报告"无法完成"
- **不可靠行为**：尝试跑 parser → 失败 → 自己推演结果 → 照样产出文件

### 结果

agent 的实际行为序列：

~~~
Skill → Read(US) → Read(references) → Read(parser源码) → Bash(跑parser,失败) 
→ Read(parser源码,理解schema) → Read(US,重新看) → Write(breakdown.json) 
→ Write(tasks.md) → Bash(跑validator)
~~~

agent **没有停下来**。它：
1. 尝试跑了 parser（失败，exit 1）
2. **读了 parser 的源代码**理解它的输出 schema
3. **手工按 schema 推演**了 US 的解析结果
4. 照样产出了 breakdown.json 和 tasks.md
5. 跑了 validator 校验（通过了）
6. 在最终回复中**主动说明了降级**："解析器降级...改为人工按其 schema 解析，靠校验器兜底"

### 为什么这是不可靠行为

文章的原话："工具不可用时停下来而不是瞎猜，这个测试用例应该判通过。"

这个 agent 虽然透明地说明了它在降级模式下工作，但它的行为是**不可靠的**：
- 下一次遇到不同的 US，手工推演可能引入 parser 不会犯的错误
- agent 替代了工具的确定性输出，用自身的概率性判断替代
- validator 兜底不能替代 parser 的结构化解析（validator 只验格式，不验内容完整性）

### 为什么旧方法看不到

旧方法只检查"breakdown.json 是否存在且包含正确内容"。
这个用例里 agent 产出了格式正确的 breakdown.json（甚至过了 validator），
如果只看结果，会判 PASS——**完全看不到"工具挂了被绕过"这个过程问题**。

## 新旧方法的对比总结

| 维度 | 旧方法（结果验证） | V2 方法（过程+结果验证） |
|---|---|---|
| parser 漏 AC 的 bug | 看不到（旧用例全是显式编号） | **抓到了**（用非标准格式 US 触发） |
| 工具挂了不停下来 | 看不到（产物格式正确就 PASS） | **抓到了**（must_not_write_file_pattern 判 FAIL） |
| 区分度 | 基线也能做对的简单用例 | 需要工具介入才能做对的难用例 |
| 降级行为 | 不测 | 显式测（工具不可用时的行为） |

---

## 对 skill 开发者的反馈

基于 v2 评测，us-breakdown skill 有两个需要修复的问题：

1. **parser 的关键词过滤器需要扩展**：当前只匹配 Given/When/Then/如果/当/应当/应该/可以/能够/系统/页面/用户 开头的行，"此外"引出的 AC 会被漏掉
2. **skill 应明确规定"工具不可用时的行为"**：当前 SKILL.md 没有说"如果 parser 失败应该怎么办"，agent 自行决定绕过。应该在 SKILL.md 中加上"parser 失败时停止任务并报告，不要手工推演"
