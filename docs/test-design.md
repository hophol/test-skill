# Skill 测试方案设计：从软件测试到 Agent Skill 测试

> 核心洞察：skill 测试和软件功能测试在"预期 vs 实际"的结构上同构，
> 但载体不同导致维度爆炸——软件的变量是固定枚举的，agent 的变量是非确定的。
> 方案必须覆盖这个差异。

---

## 一、类比：软件测试 ↔ Skill 测试的映射

| 软件测试概念 | Skill 测试对应 | 同构性 |
|---|---|---|
| 预期输入 → 期望输出 | 预期 prompt → 期望行为/产物 | 完全同构 |
| 负面测试（不该做的） | 不相关 prompt 不触发 skill | 完全同构 |
| 边界值分析 | 恰好在/不在触发范围内的 prompt | 完全同构 |
| 等价类划分 | 同类 prompt 应产生同类行为 | 完全同构 |
| 集成测试 | skill + 工具 + 多轮上下文 | 基本同构 |
| 回归测试 | 改 SKILL.md 后之前的不退步 | 基本同构 |
| Mock/Stub | 模拟工具不可用 | 基本同构 |
| 覆盖率 | 工作流步骤覆盖率 | 基本同构 |
| 单元测试 | 单轮调用验证单一行为 | 基本同构 |
|——以下开始断裂——| | |
| 确定性（同样输入→同样输出） | **非确定**（同样 prompt 可能不同行为） | 断裂 |
| 有限状态空间 | **近乎无限**（模型采样×上下文×工具状态） | 断裂 |
| 测试预言（spec 就是契约） | **模糊预言**（SKILL.md 是建议不是合同） | 断裂 |
| 二值判定（pass/fail） | **多维度**（过程对不对×结果对不对×行为可靠不可靠） | 断裂 |

---

## 二、断裂点分析：agent 的变量从哪来

软件的变量空间：
~~~
输入参数（有限枚举）
× 内部状态（有限枚举）
= 有界测试空间
~~~

Agent 的变量空间：
~~~
Prompt 措辞（同义改写即不同）
× 模型版本 / 温度 / 采样策略
× 上下文窗口内容（之前的对话历史）
× 工具可用性（搜索/API/脚本 是否正常）
× Skill 文件的解读方式（SKILL.md 是自然语言，不是代码）
× 外部服务状态
× 模型的训练数据覆盖
= 近乎无界的测试空间
~~~

**核心困难**：软件测试的"枚举所有分支"策略在这里失效——你无法枚举 agent 的所有可能行为路径。

## 三、测试方案设计

### 3.1 测试维度模型

软件测试的二维模型：
~~~
           实际做了
           做    不做
预期  做   TP    FN
预期  不做 FP    TN
~~~

Skill 测试需要扩展为四维：
~~~
维度 1：意图匹配（prompt 该不该触发 skill）
维度 2：流程合规（agent 有没有走 skill 规定的步骤）
维度 3：结果正确（产物/回复的内容对不对）
维度 4：环境状态（工具正常 / 工具降级 / 环境对抗）
~~~

四维的组合才是完整的测试用例。一个测试用例 = (意图, 流程, 结果, 环境) 的期望值组合。

### 3.2 六种测试类型

#### 类型 1：功能测试（意图 × 流程 × 结果 × 正常环境）

**类比**：软件的功能测试（正常输入→期望输出）。

**设计**：
- 选能命中 skill 介入决策点的 prompt（不是模型凭常识就能答的）
- 断言 agent 走了 skill 规定的步骤（must_call_tool）
- 断言产物正确（must_write_file + must_contain）

**示例**（us-breakdown）：
~~~
prompt: "把 docs/us-billing.md 拆解成前端任务"
断言：
  过程：must_call_tool(Bash, command_contains "us_parser.mjs")
  过程：must_call_tool(Bash, command_contains "validate_breakdown.mjs")
  结果：must_write_file_pattern("breakdown.json")
  结果：must_contain_file(["AC1","AC2","AC3","AC4","AC5"])
~~~

#### 类型 2：负面测试（不该触发 × 不该走流程）

**类比**：软件的负面测试（无效输入不崩溃）。

**设计**：
- 选明显不相关的 prompt
- 断言 skill 不被触发（should_not_call_tool）

**示例**：
~~~
prompt: "用一句话解释什么是闭包"
断言：
  must_not_call_skill
~~~

#### 类型 3：边界测试（模糊意图 × 两种可能）

**类比**：软件的边界值分析（输入在边界附近的行为）。

**设计**：
- 选"看起来相关但不完全在范围内"的 prompt
- 可以触发也可以不触发，但要验证行为的合理性

**示例**（us-breakdown）：
~~~
prompt: "帮我分析这个需求文档的优先级"
（这是需求分析，不是 US 拆解——但看起来相似）
预期：不触发（或者触发了要给出合理的说明）
~~~

#### 类型 4：降级测试（正常意图 × 工具不可用）

**类比**：软件的容错测试（外部依赖挂了不崩溃）。但有一个关键差异——

**软件的期望**：外部依赖挂了→使用 fallback→返回降级结果。
**Agent 的期望分两种**：
- **可靠行为**：尝试→失败→停下来报告（不瞎猜）→ 判 PASS
- **不可靠行为**：尝试→失败→绕过工具手工推演→产出看起来对的结果→ 判 FAIL

**设计**：
- 破坏 skill 依赖的关键工具（删掉脚本、断网、改坏配置）
- 断言 agent 的行为模式而非结果

**示例**（us-breakdown，parser 不可用）：
~~~
prompt: "把 docs/us-billing.md 拆解成前端任务"
环境：parser 脚本被替换为报错版本
断言：
  过程：must_call_tool(Bash, "us_parser.mjs")（证明 agent 尝试了）
  行为：must_not_write_file_pattern("breakdown.json")（不该绕过）
~~~

#### 类型 5：一致性测试（同一 prompt 多次运行）

**类比**：软件没有这个概念（因为确定性）。这是 skill 测试独有的。

**设计**：
- 同一 prompt 跑 N 次（N=3~5）
- 统计通过率和方差
- 方差大 = skill 的指导不够明确（agent 每次理解不同）

**判定**：
- 5/5 通过且行为一致 → 高置信
- 4/5 通过 → 可接受但需关注失败的那次
- 3/5 通过 → skill 指导不够明确，需要改进 SKILL.md
- 通过率不稳定（时而 5/5 时而 2/5）→ 环境或模型版本问题

#### 类型 6：变异测试（改 skill 后检测退步）

**类比**：软件的变异测试（改代码后测试是否捕捉到行为变化）。

**设计**：
- 修改 SKILL.md（删一条规则、改一个关键词、调整一个步骤）
- 重跑全套测试
- 如果通过率不变 → 测试的区分力不够
- 如果通过率下降 → 测试捕捉到了变异

**示例**：
~~~
原始 SKILL.md：包含"先运行解析器"
变异：删掉"先运行解析器"这一步
预期：must_call_tool(Bash, "us_parser.mjs") 开始失败
→ 证明这条断言有区分力
~~~

### 3.3 评分模型

软件测试：pass/fail 二值。
Skill 测试：需要多维评分。

~~~
用例总分 = w1 × 过程分 + w2 × 结果分 + w3 × 一致性分

过程分 = 合规步骤数 / 总步骤数
  （agent 走了 skill 规定的几步中的几步）

结果分 = 通过的断言数 / 总断言数
  （产物存在 + 内容正确 + 没有误产）

一致性分 = 通过次数 / 运行次数
  （同一 prompt 跑 N 次的稳定性）

权重建议：w1=0.4, w2=0.4, w3=0.2
（过程和结果同等重要，一致性作为置信度调整）
~~~

特殊规则：
- 过程不合规但结果正确 → 0 分（蒙对了不算）
- 过程合规但结果错误 → 过程分保留，结果分为 0
- 工具降级时停下来 → 过程满分（可靠行为加分）
- 工具降级时绕过工具 → 0 分（不可靠行为）

### 3.4 测试用例清单模板

每个 skill 应覆盖的用例矩阵：

| # | 类型 | 环境状态 | 数量 | 目的 |
|---|---|---|---|---|
| 1 | 功能测试 | 正常 | 3-5 个 | 验证核心能力 |
| 2 | 负面测试 | 正常 | 2-3 个 | 验证不误触发 |
| 3 | 边界测试 | 正常 | 2-3 个 | 验证触发边界 |
| 4 | 降级测试 | 工具不可用 | 1-2 个 | 验证可靠性行为 |
| 5 | 一致性测试 | 正常 | 1 个×5 次 | 验证稳定性 |
| 6 | 变异测试 | 正常（改skill后） | 1-2 个 | 验证测试区分力 |

**总计每个 skill 约 15-25 个测试用例。**

## 四、与软件测试方法论的系统对比

| 维度 | 软件测试 | Skill 测试 | 差异的应对 |
|---|---|---|---|
| 确定性 | 输入→输出确定 | 输入→输出概率 | 用多次运行取统计量 |
| 状态空间 | 有限可枚举 | 近乎无限 | 用等价类+边界值近似 |
| 测试预言 | spec 是契约 | SKILL.md 是建议 | 断言只验 SKILL.md 明确承诺的 |
| 判定方式 | 二值 | 多维（过程×结果×一致性） | 加权评分 |
| 覆盖率度量 | 代码行/分支 | 工作流步骤 | 断言映射到 SKILL.md 步骤 |
| Flakiness | 时序/竞态 | 模型采样/上下文 | Wilson 区间 + 多次运行 |
| Mock | 模拟外部依赖 | 模拟工具不可用 | 降级测试 |
| 回归 | diff 后全量跑 | diff 后全量跑 + 对照组 | 两臂（lift）|
| 探索性测试 | 人工随机尝试 | 对抗 prompt / prompt 注入 | 边界测试 |

## 五、实施路径

### 第一步：按模板生成用例清单

对每个待测 skill，按第 3.4 节的矩阵生成 15-25 个用例。

### 第二步：分层执行

~~~
L0 静态检查（免费，秒级）
  → 跑 plugin-eval 或类似工具
  → 不通过的先修 skill 文件

L1 路由测试（$0，秒级/用例）
  → 功能测试的正例 + 负面测试 + 边界测试
  → 早停模式，只验证是否触发

L2 行为测试（$0.2-1.3/用例，分钟级）
  → 功能测试的完整版（过程+结果断言）
  → 降级测试
  → 两臂（with/without skill）算 lift

L3 一致性测试（$1-6/用例，十分钟级）
  → 同一用例跑 5 次，统计方差
  → 发版前跑

L4 变异测试（$1-5/变异，分钟级）
  → 改 SKILL.md 后重跑 L2
  → 验证测试的区分力
~~~

### 第三步：多维评分与报告

每个 skill 的评测报告应包含：

~~~
Skill: us-breakdown
├─ 功能测试: 过程 4/5 步骤, 结果 5/5 断言 → 90%
├─ 负面测试: 3/3 不误触发 → 100%
├─ 边界测试: 2/3 正确处理模糊 prompt → 67%
├─ 降级测试: FAIL（agent 绕过了不可用的工具）
├─ 一致性: 5 次运行 4 次通过, Wilson [0.36, 0.98] → 需更多样本
├─ lift: 1.0（装了比不装好 100%）
└─ 总分: 过程 0.8 × 0.4 + 结果 0.9 × 0.4 + 一致性 0.8 × 0.2 = 0.84
~~~

## 六、关键洞察

1. **Skill 测试的"覆盖率"不是代码覆盖率，而是工作流覆盖率**——agent 走了 SKILL.md 规定的几个步骤中的几个。

2. **"蒙对了"和"可靠地对"的区分只有过程验证能做到**——这在软件测试里不存在（因为软件没有"蒙"的概念，只有"碰巧 bug 抵消"）。

3. **降级测试的期望与软件测试相反**——软件的容错测试期望"降级但不崩溃"，agent 的降级测试期望"停下来而不是瞎猜"。一个产出结果，一个不产出结果。

4. **一致性测试是 skill 独有的**——软件不需要（确定性保证了一致），agent 需要（非确定性要求统计验证）。

5. **变异测试的方向相反**——软件的变异测试改代码确认测试能抓住，skill 的变异测试改 SKILL.md 确认断言能区分"有 skill"和"没 skill"的差异。
